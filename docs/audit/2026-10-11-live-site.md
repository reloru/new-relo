## Finding 1 — `/tropics` called a post-tropical remnant a "Potential Tropical Cyclone"

Live during the audit: Isaias, 25 mph, 75 mi south of Nashville, rendered as
**"Potential Tropical Cyclone Isaias"** on `/tropics`, in `/api/tropics`'s
`classificationLabel`, and through the MCP `get_tropical_outlook` tool.

`NHC_CLASS` mapped `PTC → "Potential Tropical Cyclone"` and `PC → "Post-tropical
Cyclone"`. NHC's `PTC` is **post**-tropical. Three primary-source confirmations:

- Isaias's own advisory (MIATCPAT4): *"Post-Tropical Cyclone Isaias Advisory
  Number 18"* — classification `PTC` in `CurrentStorms.json`.
- Rachel, EP18 (MIATCPEP3): *"Post-Tropical Cyclone Rachel Advisory Number 56"*
  — also `PTC`.
- NHC's published sample, `productexamples/NHC_JSON_Sample.json`: Hilary 2023 as
  `PTC`, its advisory issued by WPC — the office that writes post-tropical
  remnant advisories.

A potential tropical cyclone is the opposite case — a disturbance not yet a
cyclone, carrying a number, never a name — which is the inverse of what the page
told readers.

**The code NHC uses for a potential tropical cyclone could not be confirmed** from
any NHC document reachable here, so the fix maps none: `PTC` becomes
"Post-tropical Cyclone" / "Ciclón postropical", `PC` is removed, and an unmapped
code renders as itself instead of as a guessed label.

## Finding 2 — `/water` showed flows for two gauges where no agency measures one

| Gauge | Shown | USGS measured |
|---|---|---|
| HSJT2, San Jacinto at Lake Houston (08072000) | 24,900 cfs | **no discharge series at all** — gage height only |
| SHLT2, San Jacinto near Sheldon (08072050) | 7,690 cfs | **−356 cfs**; −2,350 to +2,040 over the prior 12h |

Both numbers are NWPS's `status.observed.secondary`, republished faithfully — the
site was not mis-parsing. The problem is upstream:

- At HSJT2, NWPS's **own** observed series (`/stageflow/observed`) carries
  `secondary: -999` (missing) for all of the last 48 points. Only the status
  summary holds 24.9 kcfs — while Harris County sits 70% in D1 drought (US
  Drought Monitor, week of Oct 6) and the measured tributaries above the lake
  run 2–14 cfs.
- At SHLT2 the reach is tidal. USGS measures flow reversing through zero; NWPS's
  series stays between +2.21 and +7.69 kcfs — always above USGS's 12-hour
  maximum.

The discriminating evidence that this is site-specific rather than NWPS being
generally wrong: where USGS **does** measure discharge, NWPS agrees —

| Gauge | NWPS | USGS 00060 |
|---|---|---|
| HCDT2 (08067500) | 2 cfs | 2.00 |
| HFFT2 (08071250) | 3 cfs | 2.37 |
| NCET2 (08070200) | 12 cfs | 13.9 |
| GMKT2 (08067520) | none | none published |

Fixed with a `noFlow` flag on those two entries of `WATER_GAUGES`, applied in
`fetchWater()`, so the KV value, both page languages, `/api/water`, and the MCP
tool all drop the figure together. Stage stays — it is real at both, and USGS's
gage height matches it (42.46 ft; 3.65 vs 3.74 ft at different read times).

`/fishing` was never affected: it reads 08072050 from USGS directly and already
shows that station as "Water level only".

## Finding 3 — `/pollen` said it listed every counted type, and cut each list at eight

The page states *"Only types the lab actually counted today are listed"*, and the
MCP schema describes `species` as *"the types counted above zero"*.
`parsePollenCount()` ended with `found.slice(0, 8)`.

On Oct 9 the lab counted 15 nonzero molds; the page showed 8. The seven dropped
were Alternaria 38, Drechslera/Helminthosporium 16, Nigrospora 12,
Oidium/Erysiphe 10, Pithomyces 8, Rusts 6, Torula 2. They sum to 92 — exactly the
gap between the shown genera (11,334) and the group total on the same page
(11,426).

Fixed by removing the cap rather than rewording the claim; the full list was 15
lines on Oct 9. New test case built from the real
Oct 9 counts; confirmed to fail against the old `slice(0, 8)` (got 8, want 15;
got 11,334, want 11,426) before passing on the fix.

## Not changed — noted

- **`uv.peakToday` reads `0` / "Low" every evening.** EPA's hourly UV product
  rolls to the next day by evening, leaving only that night's zero-UV hours under
  today's date, so from then until midnight `/api/weather` and the MCP
  conditions tool report today's peak as 0. The homepage already hides it
  (`if (uvPeak)` in `home.js`, with a comment saying why). Left as is because
  `docs/endpoints/api/weather.md` records "Raw `0`s are kept" as a deliberate
  choice; returning `null` for a zero peak would be the minimal fix if that
  choice is revisited.
- The USGS OGC API answered this session's container with `OVER_RATE_LIMIT`
  (keyless requests). `/fishing` uses the same API keyless from the Worker and
  is fresh, so this is the container's egress, not the site — but it is the same
  shape of risk as the Google News block, and an API key from
  `api.waterdata.usgs.gov/signup/` would remove it.
