# Live-site audit — 2026-08-05

A health-and-correctness audit of the live deploy at commit `797d332`, run
against production with `curl` rather than read from source.

This is an audit, not a state file: it is dated and it is not updated in place.
Current expected state per route lives in `docs/pages/` and `docs/endpoints/`.

- Live: 40 content-page URLs (20 pages × 2 languages), 29 non-page routes swept
- Predecessor: `docs/audit/2026-08-01-post-decomposition.md`

**Result: the site is healthy.** Every route answers, every cross-cutting
invariant holds, and the data is sane. Two real defects were found — A0, a
broken scrape that silently froze `/pollen`, and A1, the monitoring gap that
let it go unnoticed.

Every claim below was checked against the live site. Where a check came back
clean it is recorded in section (b), because "we looked and it was fine" is the
part that rots silently.

> **Correction, same day.** As first written, this audit had only A1, and
> attributed the stale pollen count to HHD having stopped publishing. That was
> **wrong**, and the owner caught it by finding a published Aug 5 count the site
> was not showing. The cause was our own scrape (A0). The error is instructive
> enough to keep rather than quietly overwrite: I probed for the newer counts
> using the *same* date pattern the production parser uses, so the check
> inherited the bug it was meant to find and returned a clean 404 for every
> probe. **A verification that reuses the code under test cannot falsify it.**
> A0 below is the corrected finding; A1 stands and is strengthened — it is the
> control that would have caught A0 on Aug 4 without anyone looking.

## a. Findings

### A0. `fetchPollen()` stopped recognizing HHD's URLs, freezing `/pollen`

`/pollen` served the **Friday 2026-07-31** count for three business days while
HHD published on Aug 3, 4 and 5. The page was not broken and never errored — it
rendered a real count, correctly labelled with its own date. It had simply
stopped advancing.

**Two strict patterns, both in `src/features/pollen.js`, compounded:**

1. `pollenSlugDate()` required a hyphen between day and year
   (`-(\d{1,2})-(\d{4})`). On 2026-08-03 HHD dropped it:
   `…-wednesday-august-52026`. Every August slug parsed as `null`.
2. The index href match was lowercase-only
   (`/href="(\/services\/pollen-mold\/…)"/g`). HHD serves the same section as
   both `/services/…` and `/Services/…`, **mixing the two on one index page**.

Measured against the live index, the two compound exactly to the observed state:

```
PRODUCTION extraction (lowercase href + hyphenated date):
  null        /services/pollen-mold/…-monday-august-32026
  2026-07-31  /services/pollen-mold/…-friday-july-31-2026
  2026-07-30  /services/pollen-mold/…-thursday-july-30-2026
  → 3 of 5 slugs seen, 2 of those parseable → newest = 2026-07-31

CASE-INSENSITIVE href match: 5 candidates
  /Services/pollen-mold/…-wednesday-august-52026
  /Services/pollen-mold/…-tuesday-august-42026
  /services/pollen-mold/…-monday-august-32026
  /services/pollen-mold/…-friday-july-31-2026
  /services/pollen-mold/…-thursday-july-30-2026
```

**Why it was silent.** `fetchPollen()`'s guarantee — throw on failure *or* an
unrecognizable layout, so nothing can wipe the last good count — worked exactly
as designed and was never triggered: the index fetched fine, a slug matched, and
the July 31 page parsed cleanly into four groups. The protection covers the
count being *wiped*, not the count being *frozen*, and nothing covered the
latter.

`parsePollenCount()` was never at fault: run against the live Aug 5 page it
returns all four groups correctly. Only the URL matching was wrong.

**Fixed** by making both patterns permissive — optional day-year separator,
case-insensitive href — and leaving `parsePollenCount()` as the strict gate,
since it is the one that can tell a real layout change from a cosmetic URL
change. Verified end-to-end: `fetchPollen()` now returns `countDate:
2026-08-05`.

### A1. An aging pollen count is invisible to `/api/health`

The A0 freeze ran for three business days without anything noticing, because
`/api/health` reported the feed `ok` / `freshness: fresh` throughout, and the
overall report `ok`.

**The defect is that nothing can see it.** `/api/health` judges pollen freshness
from `data.updated` — the KV *write* time — which the cron rewrites every ~2h
whether or not `countDate` moved. A count that stops advancing is therefore
indistinguishable from one that is up to date. That is precisely the early
warning `/api/health` exists to give, and it is missing.

**A0 is no longer hypothetical proof of this.** A `countDate`-age check would
have flagged the freeze on Aug 4, the first day the count failed to advance,
instead of it surfacing when the owner noticed a published count the site was
not showing. Fixing A0 restores the data; only A1 stops the next URL change
from doing the same thing silently — and there will be a next one, since this
is a scrape of a city Drupal site that has now changed its URL shape twice.

The current rationale, in `src/api/health.js` at the pollen feed, is:

```js
// countDate is the day the count is FOR; weekends legitimately carry
// Friday's, so it is reported but never used to judge freshness.
```

That is right for a 1–3 day gap and does not cover an open-ended one. Note the
comment reasons about *why HHD might legitimately be behind* and concludes the
signal is unusable — but the freeze it needed to catch was ours, not HHD's.

**Precedent for the fix is already in the same file.** The `weather` feed's
`shape()` tests whether the forecast *window* has elapsed, with the comment:

```js
// Has the forecast WINDOW itself elapsed? `updated` only says when we
// last fetched; NWS can hand back a product whose periods have all run
// out, and that parses perfectly.
```

Pollen's `countDate` is the same failure mode — a fresh write of stale content —
and has no equivalent check. Filed as issue **#156** with a full implementation
sketch; not fixed here, at the owner's direction.

Note the correct severity is `degraded`, not `unhealthy`: a stale count is real,
usable, honestly-labelled data, not malformed. Pollen is non-critical, so that
is a `200` with detail in the body and no `503`.

### A2. Issue #93 was delivered but left open

#93 ("Pollen: add pollen counts to the site") was still open with label
`backlog` despite being fully shipped — HHD is the source it named, `/pollen`
has its own page, `get_pollen` is live, `/api/pollen` is public, and the count
is labelled measured per the AQI precedent. Closed as part of this audit.

The other three open backlog issues (#94 lightning, #95 tides, #96 historical
weather) are genuinely unstarted and were left alone.

**Both languages, every page.** All 40 URLs, not a spot-check — the rule that

English-only sweep. Spanish pages run 3–7 % larger than their English

**`http://www` in one hop.** `http://www.crosbynews.com/` → `301` →
`https://crosbynews.com/` directly, not via `https://www`. The `(not ssl)`

intermittently false-fails from a sandbox; it was clean here.

## c. Non-findings worth recording

**A transient `nearbyOzoneMonitor: "not reporting"`.** Seen mid-audit at the
22:30 cron tick, resolved to `"reporting"` at the 22:45 tick with the same
observation hour (21:00Z). That is AirNow's hourly post landing between ticks,
not a fault — the card hides gracefully in the gap, as designed.

**`/sitemap` does not list `/robots.txt`.** It lists `/sitemap.xml`, `/llms.txt`,
`/manifest.json`, the favicons and `/.well-known/api-catalog`, so the omission
looks inconsistent at a glance. It is not a drift: `docs/pages/sitemap.md`
documents the four groups and `robots.txt` is in none of them. Crawlers find
`robots.txt` by convention and never need a link. Left as-is deliberately.

**`"sin datos"` on `/es/about`.** Flagged by a text scan for outage language;
it is the privacy sentence ("sin cookies, sin anuncios, sin rastreadores, sin
datos personales"), not a data-outage state. False positive.

**`/api/tropics` is 126 bytes.** An empty `storms: []` is the normal
quiet-basin state, which the health shape check already encodes.

## d. How to re-run this

The route sweeps, header checks, canonicalization, negotiation and 404 checks
are all encoded in `/verify-site` — run that rather than re-deriving them. The
checks specific to this audit:

```bash
# PAGE_PATHS vs sitemap.xml — exact set match, both directions
curl -s https://crosbynews.com/sitemap.xml | grep -o '<loc>[^<]*</loc>' \
  | sed 's/<[^>]*>//g;s|https://crosbynews.com||' | sort

# SKILL.md digest vs the published one
curl -s https://crosbynews.com/.well-known/agent-skills/crosby-weather/SKILL.md \
  | sha256sum
curl -s https://crosbynews.com/.well-known/agent-skills/index.json

# MCP version agreement: server.json, MCP_SERVER_INFO, and the registry
curl -s "https://registry.modelcontextprotocol.io/v0.1/servers?search=com.crosbynews/weather"

# All 13 tool names present on each hand-maintained surface
curl -s https://crosbynews.com/llms.txt
curl -s https://crosbynews.com/.well-known/agent-skills/crosby-weather/SKILL.md
curl -s https://crosbynews.com/developers
curl -s https://crosbynews.com/es/developers
# plus README.md in-repo

# Pollen count age — the A1 check, until #156 lands
curl -s https://crosbynews.com/api/pollen   # compare countDate against today (CT)

# Pollen scrape coverage — the A0 check. Extract index slugs WITHOUT reusing
# pollenSlugDate's pattern, then confirm our parser agrees on every one.
curl -s https://www.houstonhealth.org/services/pollen-mold \
  | grep -oiE '/services/pollen-mold/houston-pollen-mold-count-[A-Za-z0-9-]+' | sort -u
```

**On that last one — the methodological lesson of this audit.** As first
written, the A0 probe generated candidate URLs from the same `-DD-YYYY` pattern
`pollenSlugDate()` uses, got a 404 for every one, and concluded upstream had
stopped publishing. The check inherited the exact bug it existed to find, and
returned a confident, clean, wrong answer.

Extract what the page actually links, with a pattern deliberately looser than
the production one, and compare. **A verification that shares an assumption with
the code under test cannot falsify that assumption** — it can only confirm it.
That applies well beyond this scrape: prefer checking against ground truth
(what the upstream serves, what the live site returns) over checking against a
re-derivation of our own logic.

The Spanish-link invariant and the cross-module reference rules are enforced by
`scripts/check-renders.mjs` and `scripts/check-module-refs.mjs` in the required
CI job, so they need no manual sweep — the live check above was confirmation,
not the gate.
