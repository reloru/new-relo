## c. Divergences between the docs and the code

### README documents 9 of the 15 `/api/*` endpoints

The 15 that exist: `weather`, `news`, `calendar`, `water`, `fishing`, `tropics`,
`traffic`, `pollen`, `air`, `health`, `push/vapid-key`, `push/subscribe`,
`push/unsubscribe`, `news/delete`, `news/restore`.

README lists the first nine.

**The push and news-admin omissions are intentional, and this was checked rather
than assumed.** All six are absent from `/openapi.json`, from
`/.well-known/api-catalog`, and from `llms.txt` as well — withheld consistently
across every discovery surface, not just README. They are not public data
endpoints: `/api/push/*` is internal wiring for the `/alerts` opt-in UI and
returns 503 when VAPID is unconfigured, and `/api/news/{delete,restore}` is gated
on the `ADMIN_KEY` secret, deliberately carries no CORS header, and 503s when the
secret is unset. Documenting them would advertise an owner-only control surface
for no reader benefit. **No change needed.**

**`/api/health` is a genuine gap.** It *is* documented in `openapi.json` (a full
path entry at `src/index.js:6640`), it *is* referenced in the api-catalog as every
entry's `status` link (`6371`), and it *is* in the `/verify-site` skill's route
list. Only README omits it. That is an oversight, not a policy.

### README never mentions `/privacy` or `/contact`

Verified: the only case-insensitive `contact` match in README.md is
`get_emergency_contacts`, and there is no `privacy` match at all. Both are real
content pages in both languages, both are in `sitemap.xml`, both are in
`llms.txt`, both are in the footer of every page.

### README's "no build step" is false

`README.md:85–86`, under `## Stack`:

> - No build step and no dependencies — `src/index.js` is the entire app and
>   `wrangler.jsonc` is the config.

CI's `build` job runs `npx wrangler deploy --dry-run` on every PR and every push
to `main` (`.github/workflows/deploy.yml:39`), and the production `deploy` job
`needs` it. `wrangler deploy` bundles the Worker with esbuild before upload —
that is a build step, and it has been one since the build-check job was added.
The claim was accurate when the file was 400 lines of self-contained source; it
is not accurate now. Decomposition does not *introduce* a build step; it makes
the bundling that already runs load-bearing. Rewritten in the CI-gate PR.

The "no dependencies" half of the sentence is true of the *runtime* — the Worker
imports nothing — but the repo has a pinned `wrangler` devDependency and a
lockfile, so the phrasing overstates it.

### CLAUDE.md's two other "no build step" claims are accurate and stay

Checked separately, on their own terms, as they are narrower claims about single
assets rather than about the repo:

- `CLAUDE.md:361` — "Styling: an inline `<style>` block in the rendered HTML — no
  build step, no static assets." **True.** `BASE_CSS` is a template literal
  interpolated straight into each page's `<head>`; there is no CSS pipeline, no

- `CLAUDE.md:771` — "`/sw.js` (hand-written service worker, no build step)."

Neither is swept into the README fix.

## d. Live-site issues, ranked

Nothing here is currently breaking the site. Ranked by user-visible impact.

### 1. `renderError()` blames NWS for every upstream failure — `src/index.js:1870`

The body is hardcoded:

> We couldn't reach the National Weather Service just now.

It is the 502 response for eleven routes: `/hourly`, `/alerts`, `/news`,
`/water`, `/fishing`, `/tropics`, `/traffic`, `/pollen`, `/air`, `/calendar`,
`/weather`, and the homepage. A Crosby ISD iCal failure on `/calendar`, or a
TranStar outage on `/traffic`, tells the visitor the National Weather Service is
down. On a site whose whole premise is honest sourcing, that is the wrong claim
to make by default.

It also renders `err.message` into a public `<pre>` (`1878`). It is passed
through `esc()` so it is not an injection vector, but it exposes upstream URLs
and HTTP status codes to anyone who catches a bad minute.

Fix with the homepage-hub move (decomposition step 7): take the failing source's
name as a parameter, and drop the raw message.

### 2. `loadNews()` doesn't guard against a corrupt `news` key — `src/index.js:3796`

```js
const [data, block] = await Promise.all([
  env.WEATHER.get(NEWS_KV_KEY, "json"),
  env.WEATHER.get(NEWS_BLOCKLIST_KV_KEY, "json").catch(() => null),
]);
```

The blocklist read is guarded; the news read is not. `env.WEATHER.get(k, "json")`
throws on a value that isn't valid JSON, so a malformed `news` key rejects
`loadNews` and 502s `/news`, `/news.xml` and `/api/news`.

`loadWeather` (`6228`) handles exactly this case explicitly, with a comment
saying it is "largely theoretical" but self-healing anyway. `loadNews` should
match — and it matters slightly more there, because `news` is the one key the
Worker does not own and cannot re-fetch: it is written out-of-band by
`scripts/fetch-news.mjs`, so there is no self-heal path, only degrade-to-empty.
The homepage already degrades (`8924`); the dedicated routes don't.

Fix with the news module move (decomposition step 10).

### 3. `/api/health` cannot report unhealthy — `src/index.js:8262`

```js
let updated = null;
try {
  const cached = await env.WEATHER.get(KV_KEY, "json");
  updated = cached?.updated ?? null;
} catch {}
return new Response(JSON.stringify({ status: "ok", updated }), …);
```

`status` is the string literal `"ok"` on every path. A KV outage, a corrupt
value, or a cache that has been stale for six hours all return `200 {"status":
"ok"}`. The endpoint is advertised as the `status` link of every api-catalog
entry, so anything monitoring the site through the catalog is monitoring a
constant. `updated` is the only real signal, and the caller has to compute the
staleness itself.

Not urgent — no monitor is known to depend on it — but worth correcting when the
API modules move (step 13).

### 4. `/mcp` and `/es/mcp` are pages that no page machinery knows about

Both render `<link rel="canonical">` and reciprocal hreflang tags, both are
markdown-negotiated, and `/mcp` was deliberately made indexable in 2026-07-13 so
AI Overviews can cite it. But neither is in `PAGE_PATHS` (`9097`), so neither
gets the HTTP `Link: rel="canonical"` header that all 38 other content pages get,
and neither is in `sitemap.xml` (`2071–2091`).

A third instance of the same gap, found while writing `docs/pages/mcp.md`:
**`mcpInfoHtml` emits no JSON-LD at all.** There are 19 `${JSONLD_SITE}`
interpolations for 19 content pages; `/mcp` is the 20th HTML page and has none.
CLAUDE.md's claim that "every HTML page emits schema.org JSON-LD — `JSONLD_SITE`
sitewide" is therefore inaccurate, and `/mcp` is the exception.

The consequence is small — the in-HTML canonical still does the work — but it
means the `?format=md` variants of `/mcp` don't consolidate at the HTTP layer,
and a crawler working from `sitemap.xml` will never find the page it was made
indexable for.

### 5. `/verify-site` has coverage gaps

The skill checks 44 paths. Not checked: `/mcp`, `/es/mcp`, `/radar-image`,
`/apple-touch-icon.png`, `/apple-touch-icon-precomposed.png`, `/favicon.ico`,
`/favicon.svg`, and `/.well-known/agent-skills/crosby-weather/SKILL.md`.

Two of those matter more than the rest. `/mcp` is the site's most externally
depended-on route — it is the published MCP Registry listing — and no health
check touches it. And `SKILL.md` is the file whose SHA-256 the agent-skills index
publishes at `/.well-known/agent-skills/index.json`, so a regression there breaks
a documented digest silently.

## Deployment surface (recorded so it stays true)

Nothing under `docs/` can reach production. `wrangler.jsonc` declares no
`assets`, no `site`, and no `rules` block — the only artifact uploaded is the
esbuild bundle rooted at `main` (`src/index.js`), and no file under `docs/` is
reachable by import from it. No workflow step uploads a directory. There is
nothing to exclude; the path is already outside every upload surface.

Complete list of references that a source-path change would invalidate:

| File | Reference |
|---|---|
| `wrangler.jsonc:5` | `"main": "src/index.js"` |
| `.github/workflows/deploy.yml:19` | `node --check src/index.js` |
| `.claude/skills/deploy/SKILL.md:3, 10, 22` | the same command, plus prose |
| `README.md:85–86` | "`src/index.js` is the entire app" |
| `CLAUDE.md` | 8 occurrences |

`package.json`'s only scripts are `wrangler deploy` and `wrangler dev`, neither
of which names a source path; `server.json` carries no source path at all; and no
file under `scripts/` references `src/`. Wrangler resolves the entry solely
through `wrangler.jsonc`'s `main`.
