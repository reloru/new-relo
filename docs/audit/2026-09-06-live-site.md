# Live-site audit — 2026-09-06

Routine health check, ~10 days after the 2026-08-27 content and design audit.
Read-only sweep of the deployed Worker, then a targeted investigation of the one
signal that came back wrong.

**Result: the site is healthy everywhere except `/pollen`, which has been
serving a four-day-old count since Sep 3 and has silently lost its species
breakdown entirely. Two distinct upstream changes, neither detectable from any
existing signal.** Both fixed in the same PR as this write-up.

## Finding 1 — `/pollen` frozen at Sep 2 (HHD renamed its slugs again)

`/api/pollen` served `countDate: 2026-09-02` on Sep 6. `/api/health` showed
`pollen.ok: true`, `hoursSinceAttempt` 40.7, `hoursSinceChange` 102.9.

The staleness alone proves nothing — a Friday count is correct on a Sunday. What
made it a finding is that **HHD had published on Sep 3 and Sep 4** and we did not
have them.

Established without reusing our own parser, per `CLAUDE.md`'s rule that a check
sharing code with the thing under test cannot falsify it. A loose sweep of the
live index for hrefs containing `count` returned only three, newest Sep 2 — but
the index's *visible text* listed five, newest **Friday, September 4**. The two
newest entries' hrefs simply do not contain the substring:

```
/services/pollen-mold/houston-pollen-mold-friday-september-4-2026     ← new shape
/services/pollen-mold/houston-pollen-mold-thursday-september-3-2026   ← new shape
/services/pollen-mold/houston-pollen-mold-count-wednesday-september-2-2026
```

`pollenNewestFromIndex()` anchored on the literal stem
`houston-pollen-mold-count-`, so the two newest days were invisible while the
older ones parsed fine. Fetching the Sep 4 page directly returned 200 and parsed
into all four groups — nothing about it was unreadable; it was never selected.

**This does not self-heal.** The cron gate refetches while
`countDate !== today`, which a matcher that cannot see new counts never
satisfies, so it would have stayed pinned to Sep 2 indefinitely while refetching
every 15-minute tick each weekday.

**Fourth occurrence of this exact shape in five weeks** — day-year hyphen
(08-03), path casing (08-05), month abbreviation (08-24), slug stem (09-06). Each
earlier fix relaxed the one thing that had just changed, which is why there was a
fourth.

### Independent confirmation, and the state of prior art

Searched for existing solutions before writing one.
[`hadley/houston-pollen`](https://github.com/hadley/houston-pollen) scrapes the
same HHD source daily via GitHub Actions and is actively maintained
(`collapsed/2026.parquet`; commits through Sep 3). **It is broken on exactly the
same days**: `data/2026-09-02.parquet` exists; `2026-09-03`, `2026-09-04` and
`2026-09-05` all 404. Independent corroboration that this is HHD changing
things.

Its technique is instructive as a counter-example: `scrape.R` never reads the
index, it constructs candidate URLs and tries each in turn — *"the URLS are human
created because they appear to randomly vary between a few formats."* It already
enumerated two prefixes (`houston-pollen-mold-count-`, `pollen-mold-`) and still
missed, because the new shape is a third. Enumerating known variants loses
against an upstream that renames without notice, and it is the same anti-pattern
`CLAUDE.md` warns about.

`emptyflash/houston-pollen-data` is stale (2018 HTML, pre-migration
`houstontx.gov` path). HHD publishes no JSON API; its only structured output is a
**monthly** `pollen-count-archive-YYYYMM.xlsx`, useless for daily freshness. HHD
directs programmatic requests to `pollen.mold@houstontx.gov`.

## Finding 2 — the species breakdown had silently vanished sitewide

`/api/pollen` returned `species: {tree: [], weed: [], mold: []}`, and the
"What's in the air" heading was **absent from `/pollen` altogether** — the block
renders only when a group has species, so it disappeared rather than showing
empty.

HHD's Drupal now emits list items with attributes:

```html
<li data-list-item-id="ed2e1671dd4be6f0c78c1b19f55461d18">Ambrosia (Ragweed):&nbsp;2</li>
```

`parsePollenCount()` matched only a bare `<li>`, so every attributed entry was
dropped. Confirmed by re-parsing both live pages with an attribute-tolerant
pattern: Sep 4 yields 2 weed + 8 mold genera, Sep 2 the same. **This predates the
slug change** — it was broken on the Sep 2 count already being served, and the
tree list only looked correct because that group is genuinely all zeros.

## Finding 3 — the test suite could not have caught either

`scripts/test-pollen-parse.mjs` passed throughout. Every index fixture in it
embedded `houston-pollen-mold-count`, the exact stem that had changed, and
nothing exercised `parsePollenCount`'s species branch at all. A suite built from
the format that broke last time cannot catch the format that breaks next time.

## Finding 4 — the cron retry has no floor

The pollen gate (from PR #196, Aug 22) is "do we have *today's* count yet". On a
normal publishing weekday that self-limits correctly — it stops when the morning
count lands. Nothing bounded it when the count never arrives, so it ran every
tick until midnight: 96 ticks × 2 requests ≈ 192 requests at a city health
department. That is what happened all of Friday Sep 4 (`/api/health` recorded the
last attempt at 11:45:31 PM CDT, the final tick before the weekend skip), and it
would have recurred on **Monday Sep 7, Labor Day** — a City of Houston holiday,
on which HHD does not publish.

Not a regression: #196 shipped correctly for what it was solving. This case was
simply outside it.

## What shipped

1. **Selection no longer depends on slug wording** — any href under
   `/services/pollen-mold/` whose slug yields a date, with `pollenSlugDate()` as
   the discriminator. Absorbs all four historical renames with no code change.
2. **Species markup matched with attributes** — `<li\b[^>]*>` and a regex `<ul>`
   search (an attribute on `<ul>` would make `indexOf` skip past the real list).
3. **1h floor between pollen fetch attempts**, keyed on the last successful
   write.
4. **`.github/workflows/pollen-watch.yml`** — weekdays 17:00 UTC, compares the
   date in HHD's human-readable link text against `/api/pollen`'s `countDate`
   and files a `pollen-watch` issue when HHD is ahead. Keys on nothing
   time-based, so weekends and holidays cannot trigger it; shares no failure mode
   with href matching. `.github/scripts/pollen-watch.mjs` does not import from
   `src/`.
5. **Tests rebuilt** around the real Sept 2026 HTML, plus a slug with no
   recognisable stem to prove wording-independence. Each new fixture was
   confirmed to fail against the pre-fix patterns.

## Carried forward

- The remaining silent-freeze hole: if HHD changes the **date format** inside the
  slug, new links stop yielding a date and selection falls back to an older page.
  The parser fix does not cover this; the watchdog does, since it doesn't care
  why a count was missed.
- `pollen-watch` cannot escalate to `@claude` itself — it posts as
  `github-actions[bot]` and `claude.yml` skips bot senders by design. Allowing
  that single identity is defensible and much narrower than `"*"`, but requires
  relaxing the `sender.type != 'Bot'` job guard in the same commit. Not done
  here; the issue notifies the owner instead.
- No other feed was found to have this failure shape, but none of the other
  scrapers (burnban, traffic, tropics) has an equivalent cross-check. The
  watchdog pattern generalizes if it proves out.
